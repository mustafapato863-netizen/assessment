# AssessFlow Planning Pack

Prepared: 10 August 2026
Version: 1.0 Draft

## Purpose
This pack is the reference baseline for the AssessFlow employee assessment module covering Promotion, Internal Mobility, and Role Realignment.

## Documents

1. `01_AssessFlow_BRD_v1.0.docx` - business scope, roles, requirements, rules, reports, MVP decisions, and acceptance criteria.
2. `02_AssessFlow_Workflow_Status_Matrix_v1.0.docx` - statuses, transitions, owners, eligibility gate, approvals, exceptions, SLA guidance, and audit events.
3. `03_AssessFlow_ERD_Data_Dictionary_v1.0.docx` - relational data model, core entities/fields, history, attachments, and future optional scoring model.
4. `04_AssessFlow_Screen_Requirements_v1.0.docx` - navigation, screen inventory, fields, actions, permissions, validations, and scoring-aware UX.
5. `05_AssessFlow_Technical_Technology_Guidelines_v1.0.docx` - architecture, stack, security, data, API, testing, DevOps, and the scoring feature architecture.

## Core Decisions for MVP

- Requester: Technical Manager or HR/Talent by default.
- Assessment reasons: Internal Mobility, Promotion, Role Realignment.
- Eligibility is a required gate before normal assessment planning.
- Assessment method is based on target level + role complexity + assessment reason.
- Supported methods: CBI, Case Study / Work Sample, Roleplay.
- Assessment Result is separate from Business Recommendation.
- Result values: Ready Now, Ready with Development, Not Ready, Incomplete.
- Numeric scoring is **not mandatory and is disabled by default in MVP**.
- The architecture is future-ready for optional scoring profiles/components without changing the core workflow.
- Downgrading/demotion is not an automatic result or recommendation generated by the assessment engine.

## Planning Authority
The BRD defines what the module must achieve. The Workflow Matrix defines allowed state movement. The Data Dictionary defines information structure and ownership. The Screen Requirements define user interaction. The Technical Guidelines define how the solution is engineered and operated.

Changes to core terminology, eligibility gates, result/recommendation separation, status transitions, approval routing, or scoring governance should be made as explicit controlled decisions and reflected across the relevant documents.
